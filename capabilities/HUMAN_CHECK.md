# Human verification checklist — capabilities/ pipeline

Purpose: verify the dataset deliverables with your own eyes and your own terminal,
so you can defend every number without an AI open. ~20 minutes on the Mac,
~5 on the Linux box. Written 2026-08-25 after two independent machine audits
(both all-PASS); this file is the human layer on top.

## The exact files to look through, in order

| #   | File                                                                 | What you're checking                                                  |
| --- | -------------------------------------------------------------------- | --------------------------------------------------------------------- |
| 1   | `capabilities/README.md`                                             | Read fully — this is the narration you'll give Chirag                 |
| 2   | `capabilities/sources_manifest.json`                                 | Where every byte came from (URLs, revisions, SHA-256)                 |
| 3   | `capabilities/acquire.py`                                            | The ~250 commented lines that did the work — read once, top to bottom |

| 7   | `capabilities/validation_report.json`                                | The machine's claims — you re-derive two of them below                |

## Step-by-step (Mac, from the repo root)

**1. Counts (30 sec).** `wc -l capabilities/*.jsonl`
Expect: gpqa 448 · ifeval 541 · mmlu_pro 12102 · omni_math 4428 · wildbench 1024.

**2. Provenance is real (3 min).** Open `sources_manifest.json`, copy the MMLU-Pro
test-parquet URL (the `/resolve/b189ec76…/` one) into your browser — it should
download. That URL form is immutable: same link, same bytes, forever. Note that
every input has a `sha256` — that's what `acquire.py` enforces on re-download.

**3. Row-level truth (5 min) — the most important step.**
`sed -n '1p' capabilities/mmlu_pro.jsonl | python3 -m json.tool`
Then open https://huggingface.co/datasets/TIGER-Lab/MMLU-Pro/viewer and compare
question text, the 10 options, and the answer letter character-for-character.
Repeat with a middle row: `sed -n '6000p' …`. Then one row each of
`omni_math.jsonl` and `ifeval.jsonl` against their viewers.

**4. GPQA privacy (2 min).**
`sed -n '1p' capabilities/gpqa_main.jsonl | python3 -m json.tool`
Expect `prompt_text`, `choices`, and `grading.gold` all `null`; only IDs, domains,
and hashes. Then `grep -c "reaction\|molecule\|electron" capabilities/gpqa_main.jsonl`
→ expect 0. The full text lives only in `capabilities/restricted_local/` (gitignored;
regenerated by `acquire.py`) — never in git, the Doc, or Slack.

**5. Run the validator yourself (1 min).** `python3 capabilities/validate.py`
Expect `"status": "PASS"` and zero hard failures.

**6. Re-derive one claim by hand (2 min)** — pick the loaded one:
`head -200 <(grep '"split":"test"' capabilities/mmlu_pro.jsonl) | grep -o '"category":"[^"]*"' | sort | uniq -c`
Expect: `200 "category":"business"` — the first-200 ordering problem you're
raising with Chirag, reproduced by your own shell.

**7. Git/GitHub (2 min).** `git log --oneline -5` shows the four new commits;
on GitHub switch the branch dropdown to `codex/reap-governance` and confirm
`capabilities/` shows the scripts + manifest + sanitized GPQA (the four open-text
JSONLs are intentionally absent — reacquire-locally convention).

## Linux box (5 min, run over your own ssh)

```bash
git clone https://github.com/cwklurks/effort-atlas.git && cd effort-atlas
git checkout codex/reap-governance
uv sync --python 3.12.8 --extra capabilities
uv run python capabilities/acquire.py && uv run python capabilities/validate.py \
  2>&1 | tee reap/linux_handoff/REPRO_$(date +%F).txt
sha256sum capabilities/*.jsonl | tee -a reap/linux_handoff/REPRO_$(date +%F).txt
```
Commit the `REPRO_<date>.txt` log. Without a log showing **acquire and validate both
succeeding on Linux**, the cross-machine claim is undocumented (the 2026-08-25 check

Expect PASS, and these hashes (from the audited Mac copies) to match exactly —

## Known limits of the machine checks (be able to say these out loud)

1. The "canary absent" check on GPQA is weak evidence — the pinned upstream copy
   carries no canary to leak. The load-bearing privacy checks are the null-field
   and string-length scans (both pass).
2. `validation_report.json` says `restricted_file_present: true` — true only on a
   machine where `acquire.py` has run; a fresh clone shows `false` until then.
   That's by design, not a failure.
3. The GPQA `row_hash_failures: 0` line is not-applicable-by-construction (its
   hashes cover the unsanitized rows); the real integrity evidence is the 448/448
   sanitized↔restricted hash correspondence, independently reconfirmed 2026-08-25.
